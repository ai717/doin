## 1.3 核心玩法

> 本作对标经典 QQ 游戏《连连看》/ Onet Master 的**三线连通判定**（0 折直连 / 1 折 / 2 折，禁止斜线，路径可绕出棋盘外圈）、麻将牌"符号一眼可辨"的设计原则，以及经典连连看的"提示 / 洗牌 / 无解自动重排"成熟兜底机制。
> 差异化定位为**夜市灯牌 · 琉璃瓷片**题材 + **路径即美学**（折线按折数依次点亮）+ 桌面双栏沉浸舞台。不得复制任何商业游戏的名称、代码、美术资源或外部文件。

### 1.3.1 盘面构成

- **实心区**：10 列 × 8 行 = 80 个实心格，瓷片只能落在实心格上。
- **外圈通道**：实心区四周各扩 1 圈永久空格 → **逻辑盘 12 列 × 10 行**。外圈不可放块，只作为折线通道（经典"出界绕行"，必须保留）。
- **坐标约定**：`row ∈ [0,9]`，`col ∈ [0,11]`；实心区为 `row ∈ [1,8]` 且 `col ∈ [1,10]`。`board[row][col] === 0` 表示空（可通行），`> 0` 表示图案 id（1..12）。
- **图案**：每种图案的总数**必须为偶数**（成对放置）。数量按关卡参数表分配，各图案计数互不相等亦允许，但每个计数必须是偶数。
- **主题**：抽象琉璃几何母题，共 12 种（详见 1.3.7）。

### 1.3.2 合法操作与判定

1. 先点一枚瓷片 → 进入"已选中"态（外圈铜线呼吸 + 轻微浮起）。
2. 再点第二枚瓷片 → 触发判定。**同时满足**以下三条才成立：
   - 两枚图案 id 相同，且不是同一格；
   - 存在一条**仅由水平 / 垂直段组成**的折线连通两者，**拐点数 ≤ 2**（即最多 3 段直线），**禁止对角线**；
   - 折线经过的所有格（不含两个端点自身）必须为空（`board === 0`），**包含外圈通道格**。
3. 判定通过：先画折线（按折数依次点亮），再让两枚瓷片碎成粒子消失。
4. 判定失败：**绝不清除第一枚的选中态**（试探友好）。第二枚轻抖 240ms 后保持第一枚选中。

**"绝不清除第一枚"的精确口径**（避免实现歧义）：

| 玩家动作 | 结果 |
| --- | --- |
| 再点已选中的那一枚 | 取消选中 |
| 点空白格 / 外圈格 / 已消除格 | 取消选中 |
| 点图案相同但**不可连通**的第二枚 | 第二枚抖动 240ms；**第一枚保持选中** |
| 点图案不同的第二枚 | **改选为第二枚**（第一枚取消选中，新块进入选中态），并抖动 180ms |
| 按 Esc / 拖出棋盘松手 | 取消选中 |

### 1.3.3 折线求解算法（engine 唯一权威，必须按此实现）

`findLinkPath(board, a, b)` → `{ cells: [{r,c}, …], folds: 0|1|2 } | null`

- `cells` 为折线的完整节点序列，首元素 = a，末元素 = b，中间元素为拐点；节点一律取**格中心**。
- 判定顺序与返回优先级（**确定性，保证提示与动画可复现**）：
  1. **0 折（直连）**：a、b 同行或同列，且两者之间（不含端点）全为空。
  2. **1 折**：候选拐点仅两个 —— `(a.r, b.c)` 与 `(b.r, a.c)`。拐点必须为空，且"a→拐点"与"拐点→b"两段各自畅通。按 `(a.r, b.c)` 优先于 `(b.r, a.c)` 的固定序返回。
  3. **2 折**：以 a 为起点向四个方向逐格扫描（遇非空格即停），得到候选空格集合 P；同样以 b 为起点向四个方向扫描得到集合 Q。对每一对 `(p, q)`，若 p 与 q 同行或同列、`p !== q`、且 p 与 q 之间畅通，则成立。返回**排序后第一条**：排序键依次为 ① 折线总格数最短 → ② 拐点行号+列号之和最小（更靠上、靠左）→ ③ p 与 q 的行列序稳定比较。
- 复杂度 O(R·C·(R+C))，逻辑盘 12×10，可忽略。
- `hasAnyPair(board)`：扫描全盘所有同图案对，任一可连即返回 true（用于可解性校验与死局检测）。必须与 `findLinkPath` 共用同一份判定代码，不得重复实现。
- `findHint(board)`：返回**第一条**可消对（沿用 `hasAnyPair` 的扫描序），用于提示。

### 1.3.4 完成 / 失败条件

- **胜**：限时内清空全部实心格上的瓷片（`board` 实心区全为 0）。
- **负**：倒计时归零且盘面未清空。
- **无"步数用尽"失败**。洗牌次数用尽且**自动兜底洗牌连续 50 次仍无法产生可消对**时，本关失败并提示"重玩"（理论上概率极低，见 1.3.6）。

### 1.3.5 交互方式（鼠标 / 触摸 / 键盘三通）

- **鼠标**：左键单击选中与配对；按下后拖出棋盘区域再松手 = 取消选中。**核心操作不得依赖 hover**。
- **触摸**：轻点选中第一枚，再轻点第二枚；触屏无 hover 语义，全部反馈由选中态与抖动承担。
- **键盘**：
  - `↑ ↓ ← →` 或 `W A S D`：在当前焦点格所在方向上，跳到**最近的一枚仍有瓷片的实心格**（跳过空格；该方向若无任何有块格则不动）。焦点格必须有清晰的暖铜虚线焦点环。
  - `Enter` 或 `Space`：选中 / 发起配对（等价于单击）。
  - `Esc`：取消选中。
  - `H`：提示（等价于"提示"按钮；次数为 0 时无效果且不报错）。
  - `R`：主动洗牌（等价于"洗牌"按钮；次数为 0 时无效果且不报错）。
  - `P`：暂停 / 继续。
  - 所有快捷键必须在输入框聚焦时失效（本作无输入框，按此约定实现即可），且 `Space` / 方向键必须 `preventDefault()`，避免页面滚动。

### 1.3.6 可解性与无死局策略（必须严格按此实现）

**可解性口径（三层保证 + 一处诚实声明）**：

1. **成对不变量**：每种图案的总数恒为偶数。生成与洗牌都不得破坏此不变量 → 全盘在数量上必然可消尽。
2. **可用性不变量（可判定、可测试）**：**开局**与**每一次成功消除之后**，立即调用 `hasAnyPair(board)`：
   - 结果为 false → **自动洗牌**（不消耗玩家主动洗牌次数），重复至 true 或达到 **50 次**上限；
   - 达到 50 次仍 false 且盘上**还有冰封壳**（见 1.3.15）→ **融壳兜底**：把全部冰封壳解冻成裸块，再继续洗牌至有解；
   - 达到 50 次仍 false 且无壳可融 → 本关失败（提示"重玩"）。
   → 玩家**永远不会面对无棋可下的死盘**。
   ⚠️ `hasAnyPair` 必须**跳过带壳块**（带壳块不可点选，把壳当作可用配对是错的）。
3. **洗牌等价性**：洗牌只置换"剩余瓷片的位置"，**不改变任何图案的计数**（保持不变量 1），且**不移动外圈**（外圈恒空）。**带壳状态随值一起被置换**，洗牌不得单独改变壳的数量。
4. **生成期校验**：开局布盘（含套壳）后必须通过不变量 2 的同一检查；未通过则用**同一 PRNG 流**继续取样重排，最多 200 次。

**诚实声明（必须写进代码注释）**：本作**不**对"存在完整消除序列"做全局回溯穷举 —— 80 格状态空间不可行。全局可解性由"不变量 1 + 2 + 3"共同保证：任何时刻都存在合法操作，且总量必然可消尽；若出现局部僵局，由不变量 2 的自动洗牌立即化解。这与经典 QQ 连连看的成熟口径一致。

**PRNG**：必须使用可注入种子的 `mulberry32`。种子派生：

```
hashSeed(str) -> uint32   // FNV-1a 32 位
levelSeed(L)  = hashSeed("pair-link:" + L)
```

洗牌使用**同一 PRNG 实例的后续取样**（不在洗牌时重新播种），保证"同一关卡 + 同一操作序列 → 完全可复现"。测试必须断言该确定性。

章节主题与递进：

**参数公式（必须在 engine 内确定性生成，禁止手写 36 行散落常量）**：

设 `L ∈ [1,36]`，章 `c = ceil(L / 12)`，章内序号 `k = L - 12·(c-1)`，`k ∈ [1,12]`。

```
图案种类 S(L) = [6, 8, 10][c-1] + floor((k - 1) / 4)          // 每章内 4 关一档
实心块数 N(L) = 56 + 8·(c - 1) + 4·floor((k - 1) / 4)         // 恒为偶数
每格基准秒 b(L) = [2.20, 2.02, 1.87][c-1]
时限 T(L) = ceil(N(L) × b(L))                                  // 秒
提示次数 = 3（每关固定）
主动洗牌次数 = 2（每关固定）
冰封壳数 F(L) = [0, 4, 8][c-1] + [0, 1, 2][c-1] × floor((k - 1) / 4)
                // 第 1 章恒 0；第 2 章 4/5/6；第 3 章 8/10/12
```

**计数分配规则**：把 N 块按 S 种图案分配，使每种计数为**偶数**且各计数差不超过 2（如 N=56, S=6 → 10,10,10,10,8,8）。分配结果由关卡种子决定，但**必须满足**：`min(每種计数) ≥ 2`（保证每种图案至少成对出现一次）。

### 1.3.9 计分规则（唯一口径在 `js/score.mjs`，UI 不得自算）

| 项 | 规则 |
| --- | --- |
| 基础分 | 每成功消除一对 **+100** |
| 折线奖励 | 0 折 **+0**；1 折 **+10**；2 折 **+30**（鼓励绕路破局） |
| 连击奖励 | 距上次成功消除 **≤ 3.00 秒**内再消一对 → 连击 +1，额外 **+50 × 连击数**（连击从 0 起，第二次连消为连击 1） |
| 剩余时间 | 每剩 1 秒 **+10**（关卡结算时一次性计入，向下取整到秒） |
| 未用道具 | 每剩 1 次提示 **+80**；每剩 1 次主动洗牌 **+80** |
| 连击峰值 | 记录本关 `comboPeak`（用于星级） |

**连击窗口口径**：窗口为 3.00 秒，起点为上一次成功消除的完成时刻；**暂停时窗口冻结**（`Paused` 期间不计时）；窗口超时后连击归零。失败时连击立即归零。

**算例（必须能被测试复现）**：第 1 关，玩家在第 10 秒用**两折**路径消掉第 4 对（此时连击 = 4）→ 单次得分 = `100 + 30 + 50 × 4 = 330`。若该关随后在第 40 秒清盘（T=124），剩 84 秒，提示剩 3、洗牌剩 2 → 结算加 = `84 × 10 + 3 × 80 + 2 × 80 = 840 + 240 + 160 = 1240`。

**分数钳制**：`score.mjs` 必须把单关总分钳制在 `[0, 9999999]` 内，且永不出现负数或 `NaN`。

### 1.3.10 星级评价（每关 1–3 星）

| 星 | 条件 |
| --- | --- |
| ★ | 通关（清空盘面） |
| ★★ | 通关 **且** 结算时剩余时间比例 ≥ 25% **且** 本关主动洗牌次数 ≤ 1 |
| ★★★ | 通关 **且** 结算时剩余时间比例 ≥ 40% **且** 本关主动洗牌次数 = 0 **且** 连击峰值 ≥ 4 |

- 剩余时间比例 = `remainingMs / (T × 1000)`。
- 星级只增不减：若本次星数低于历史记录，**保留历史星数**，但分数仍取历史最高。
- 主动洗牌次数**不含**自动兜底洗牌。

### 1.3.11 局内道具（每关限额，不回满）

- **提示 ×3**：高亮一对可消（两枚瓷片同时亮起暖铜脉冲 + 折线以虚线预演 1.5 秒），**不代消**。次数 0 时按钮置灰且无效果。
- **洗牌 ×2**：打乱剩余瓷片位置（保持计数与可解性不变量）。次数 0 时按钮置灰且无效果。
- 每次使用立即扣减并更新 HUD 上的印章计数。

### 1.3.12 次模式 A：无尽冲分

- **入口**：开始面板上的"无尽冲分"按钮。
- **起始盘**：第 1 关参数（S=6, N=56, T=124s）。
- **盘数递进**：第 n 盘使用 `L = min(36, n)` 的关卡参数（第 36 盘起恒用第 36 关参数），即"同一难度池循环"。
- **每盘独立倒计时**；清盘瞬间该盘剩余时间 ×10 计入总分。
- **连击倍率跨盘继承**：`chainMult = min(4.0, 1 + 0.25 × clearedBoards)`，作用于**基础分与折线奖励**（连击奖励不乘）。连击计数本身**跨盘重置为 0**（跨盘瞬间窗口必然超时）。
- **结算**：任一盘倒计时归零 → 结算总分，写入无尽最高分 `endlessBest`。
- **不占用**主线关卡进度与 `current` 槽位。

### 1.3.12b 次模式 B：每日一盘（拍板项，本任务书按 2B 落地）

门户"今日挑战"型入口，**全服同题**。

- **入口**：开始面板上的"今日一盘"按钮（`#btn-daily`）。
- **题面派生（必须确定性，禁止用 `Math.random()`）**：
  ```
  dateKey = 本地时区 YYYY-MM-DD                       // 不能用 UTC，否则跨时区不同题
  L       = hashSeed("pair-link:daily:" + dateKey) % 36 + 1   // 挑关卡参数
  seed    = hashSeed("pair-link:daily-board:" + dateKey)      // 出盘面种子
  ```
- **确定性**：同一天、同一关卡参数 + 同一种子 → **逐格完全相同**的盘面。刷新页面、点"重玩"都必须给同一副盘面（公平重试）。
- **只记录当日最佳**：结算写入 `daily: { dateKey, bestScore }`。跨天时 `dailyBest()` 因 `dateKey` 不符自然返回 0。
- **与主线完全解耦（硬性红线）**：进入 / 游玩 / 结算每日盘，**一律不得**改动 `unlocked`、`levels`、`lastLevel`。
- **无"下一关"**：结算面板按钮为"返回选关"。
- **HUD 差异**：关卡匾额显示 `MM-DD`（`shortDateKey`）而不是关卡号；章名显示"今日灯市"。

### 1.3.15 冰封壳（特殊块，拍板项 1B）

第 2/3 章出现的特殊块（数量见 1.3.8 的 `F(L)`）。

- **表现**：瓷片表面覆一层霜壳（`.tile::after` 画霜层 + 两道裂纹 + inset 冷光阴影），鼠标指针 `cursor: not-allowed`。
- **规则**：**带壳瓷片不可点选、不参与配对**。点它 → `action.type === "frozen"`，抖动一下（冰蓝 `iceShake`）+ 提示"这块瓷片被冰封住了，先消掉它周围的瓷片。"
- **震碎条件**：当**它周围 8 邻域（含斜向）**内的瓷片被消除时，壳立即震碎（霜层炸开 `iceShatter` 动效 + 播报），该瓷片恢复为可点选。
  ⚠️ 邻域判定必须**含斜向**（`AROUND8`），且传入坐标要**去重**（同一格可能既是 first 又是 last）。
- **值编码（强烈建议照此实现）**：棋盘值 `v ∈ [1,12]` 为裸块，`v + MOTIF_COUNT ∈ [13,24]` 表示带壳。
  - 好处：「非 0 即有块」的判定零改动；`shuffleBoard` 置换值数组时壳自动跟随；无需平行 `frozen` 数组。
  - 读母题一律走 `motifOf(v)`（`v > 12 ? v - 12 : v`），判壳走 `isFrozenValue(v)`。
- **可解性联动**：`hasAnyPair` 必须跳过带壳块；死盘兜底在洗牌无果后**融壳**（`meltAll`），见 1.3.6。
- **无障碍**：带壳格的 `aria-label` 追加"冰封"（如"第 2 行第 9 列，回纹，冰封"）。
- **动效降级**：震碎 / 融壳动效必须受 `prefers-reduced-motion: reduce` 约束（压成瞬移）。

## 1.4 视觉方向

**题材关键词**：夜市灯牌、琉璃瓷片、暖铜描边、深墨底、折线霓虹。

- **主色**：暖铜 `#c9863f` / 绯红灯丝 `#e2503f`；底色深墨褐 `#1a1210` → `#241a15`（**避开**门户已饱和的大面积蓝紫、青绿、玫瑰粉、暖橙金）。
- **辅助色**：琥珀 `#e8b768`、米白瓷 `#f3e6d2`、极淡网格 `rgba(243,230,210,0.07)`。
- **背景氛围**：两团绯红 / 暖铜径向光晕缓慢 drift（18s / 24s 交替）+ 内联 SVG `feTurbulence` 噪点 data URI 叠加（opacity ≤ 0.05）+ 柔和暗角。**零外链**。
- **瓷片**：琉璃质感 —— 内联 SVG 线性渐变（左上高光 → 右下加深）+ 内侧高光斜切 + 1px 暖铜描边 + 双层软阴影（`0 2px 0 rgba(0,0,0,.35), 0 6px 14px rgba(0,0,0,.4)`）。
- **外圈通道**：以极淡网格线（`rgba(243,230,210,0.07)`）暗示"可绕行"，不接收点击。
- **选中态**：瓷片外圈铜线呼吸（`box-shadow` 亮度 0.9s 循环）+ `translateY(-2px)`。
- **非法配对**：短促朱红抖动（`translateX` ±4px × 3 次，240ms）。
- **合法消除**：折线**按折数依次点亮** —— 0 折 1 段（90ms）、1 折 2 段（90ms × 2）、2 折 3 段（90ms × 3，拐角处停顿 60ms 强化"算路成功"）；随后两枚瓷片碎成 12–16 颗琉璃粒子，沿折线向**折线中点**收束并在 420ms 内淡出。
- **通道呼吸**：每对被消除后，其原位渲染一层 420ms 微光渐隐，帮助玩家看见新开口。
- **连击 ≥ 3**：侧栏连击灯牌闪一次（0.35s）+ 棋盘边缘一圈暖光脉冲（0.5s）。
- **结算仪式感**：遮罩浮现 → 星级按 180ms 阶梯依次点亮（未达成的星为暗铜空槽）→ 分数明细逐行浮现 → 若破纪录则弹出"新纪录"徽章 + 粒子喷发。

**桌面端（≥900px）双栏沉浸舞台**：

- 左 / 中：**主舞台** —— 深墨底灯箱上的瓷片棋盘，逻辑盘 12×10 等比自适应，`max-height: calc(100dvh - 120px)`；外圈通道以极淡网格呈现。
- 右侧**侧栏**（宽 300–340px，纵向 flex）：关卡匾额 / 倒计时沙漏（环形进度 + 数字）/ 连击灯牌（含 3 秒窗口环）/ 得分与最高分（徽章化 + 数值 bump）/ 星级槽 / 提示印章 ×3 / 洗牌印章 ×2 / 暂停·重玩·音效·语言·说明按钮台。
- **不得**出现大面积黑边、手机外壳、竖屏模拟框或生硬居中黑色容器；页面整体不得锁定为 9:16。

**移动端（≤768px）单列**：棋盘占上方约 70% 高度，底部通栏收纳计时、连击、得分与道具按钮；取消侧栏装饰文案与光晕动画的强度。

**封面提案**（门户方制作，供承接方理解视觉基调）：3D 软胶质感，单一居中主体 —— **两枚相同琉璃瓷片被一道两折霓虹线穿起，线的拐角挂一滴铜光**；背景深墨底 + 绯红灯晕；**零文字**；640×640 WebP。

## 1.5 音效

**包含音效**（默认，不得省略 `js/audio.mjs`）。全部使用原生 Web Audio API 程序化合成，**严禁外部音频文件**。

| 事件 | 合成方案 |
| --- | --- |
| 选中 `select` | sine 660Hz，60ms，指数衰减，gain 0.08 |
| 取消选中 `deselect` | sine 440Hz，50ms，gain 0.06 |
| 非法配对 `invalid` | triangle 180Hz + 140ms 内快速颤音，gain 0.10 |
| 折线点亮 `link` | 按折数取音：0 折 523Hz / 1 折 659Hz / 2 折 784Hz；每个拐点额外触发一次 80ms 上滑音 |
| 消除 `clear` | 短白噪（30ms）+ 880Hz bell 220ms |
| 连击 `combo(n)` | 音高 `880 × 2^(min(n,6)/12)`，双音叠加 180ms |
| 提示 `hint` | 1244Hz 双音（间隔 70ms） |
| 洗牌 `shuffle` | 噪声扫频 300ms（`bandpass` 中心频率 400→2400Hz） |
| 过关 `win` | C–E–G 上行三音琶音（523/659/784Hz，间隔 120ms） |
| 失败 `lose` | 下行两音（392→262Hz，间隔 160ms） |

要求：在用户首次手势（"开始游戏"按钮）时解锁 `AudioContext`；静音时静默降级；浏览器不支持 Web Audio 时**不得抛错**。

### 渲染策略裁决

本游戏属于**离散网格益智**玩法，采用 **DOM/CSS Grid 承载棋盘与瓷片 + Canvas 2D 覆盖层绘制折线与粒子特效**的双轨方案：

- 瓷片 = 语义化 DOM 元素（`<button>` 或带 `role="gridcell"` 的节点），天然获得键盘焦点、`aria-label` 与屏幕阅读器支持。

- **坐标同步**：渲染前用 `#board.getBoundingClientRect()` 取实尺寸，按逻辑盘 12×10 换算格中心；DPR 用 `window.devicePixelRatio`（上限 2）设置物理分辨率；`ResizeObserver` 监听 `#board-wrap` 变化后重算并重绘。
- 所有 HUD、按钮、菜单、说明、结算文本**必须**留在语义化 DOM 层。
- **不得**为了"看起来高级"引入 Three.js。

- 不得在复杂连续运动场景中滥用大量 DOM 节点。
- 本游戏**离散网格益智（连连看 / 配对通路）**属于**离散网格玩法**，默认优先使用 **DOM/CSS Grid 棋盘 + Canvas 2D 特效覆盖层**（见 1.6 裁决）。
- 如使用 Canvas，可将棋盘、路径、背景动效和完成特效绘制在 Canvas 中，但键盘操作、按钮、说明和 HUD 仍必须有 DOM 语义支持。

**【游戏舞台布局要求】**

桌面端必须像一个完整的宽屏游戏页面，而不是手机网页套在桌面中央。必须遵守：

- 游戏舞台优先占据浏览器主要可视区域
- 桌面端使用宽屏、舒展的布局
- 游戏区域、HUD 和操作按钮应集中在舞台附近
- 可以有紧凑的游戏工具栏、HUD 或返回按钮
- 不得制作传统门户网站式的大页头、营销文案区和页尾
- 不得把整个游戏限制成窄窄的手机屏幕样式
- 不得在桌面端出现大面积黑边、手机外壳、竖屏模拟框或生硬的居中黑色容器
- 不得把页面整体锁定为 9:16 手机比例
- 棋盘本身可以保持正方形或固定比例，但整个页面不应模拟手机竖屏
- 桌面宽屏下应充分利用可用空间，视觉上更像打开了一款游戏
- 移动端仍要自然收缩，保证 390px 宽视口不横向溢出
- 不得依赖 hover 才能完成核心操作

**【零外链资源与自包含底线】**

- 使用原生 HTML5、CSS3 和 JavaScript ES Modules
- 默认零依赖、零构建、零 npm
- 严禁外部 CDN、远程 API、在线字体和远程图片
- 只使用系统字体栈，不加载 WebFont
- 禁止使用 `alert()` 作为游戏反馈
- 普通反馈使用页面内 DOM toast、提示区或结算面板
- 破坏性操作（例如清空存档）可以使用 `confirm()`，其他交互不得依赖原生模态框

**【Three.js 可选规范】**

Three.js 只能作为受控的可选技术，不是默认技术栈。只有在游戏确实需要真实 3D 场景、摄像机与空间层次、光照与材质、3D 模型、空间粒子、WebGL 后处理，或明确依赖三维表现才能成立的玩法时才允许使用。必须遵守：

- 简单 2D、棋盘、网格和文字玩法不得为了"看起来高级"强行使用 Three.js
- 不得让大模型临时伪造、手写或截断 Three.js 源码
- 不得从 CDN、远程 URL 或 npm 加载 Three.js
- 只能引用项目方已经预置的本地文件：`games/<slug>/libs/three.module.js`
- 如果项目方没有提供该文件，必须改用原生 Canvas/DOM，不得留下未满足的依赖
- Three.js 只能放在 `render.mjs` 或其他视觉模块中
- `engine.mjs` 不得 import Three.js，也不得接触 DOM、Canvas 或 WebGL
- Three.js 本地 import 必须使用相对路径和 `?v=dev`
- 必须处理 DPR、ResizeObserver、逻辑尺寸与物理尺寸同步
- `setPixelRatio()` 必须设置合理上限，避免高分屏显存和性能异常
- 必须处理 WebGL 不可用或 context loss 的情况
- 重玩、切换关卡或销毁场景时释放 geometry、material、texture、renderer 等资源

**本任务裁决：不使用 Three.js。**

**【音效发生器】**

本任务**包含音效**（见 1.5）：

- 必须使用原生 Web Audio API
- 使用振荡器、合成器或程序化音效
- 在用户首次手势（例如"开始游戏"按钮）时解锁 AudioContext
- 静音时静默降级
- 浏览器不支持 Web Audio 时不得抛错
- 严禁外部音频文件

**【视觉图元】**

- 优先使用 CSS、内联 SVG、Canvas 或 Three.js 实时绘制
- 严禁引入外部位图
- 禁止使用外部图片 URL
- 不制作带文字、logo 或水印的游戏内素材

- `js/main.mjs`
  - 入口装配；绑定按钮、Pointer、Touch、Mouse、Keyboard 和 ResizeObserver
  - 初始化 i18n、storage、audio、game、render、ui
  - 不得绕过 engine 直接修改游戏规则

六、画布、交互质量与状态底线

====================

**【Canvas / WebGL 规范】**

如果启用 Canvas 或 WebGL：

- 根据 `window.devicePixelRatio` 设置物理分辨率
- CSS 维持逻辑尺寸
- 使用 `ResizeObserver` 或 resize 事件同步尺寸
- 指针、触摸和鼠标坐标必须通过 `getBoundingClientRect()` 正确换算
- 不得假设 CSS 尺寸等于 Canvas 物理像素
- 连续运动必须基于 Delta Time
- 每帧 dt 必须设置合理上限，例如 `Math.min(dt, 0.1)`
- 复杂物理使用固定时间步累计更新
- 浏览器后台恢复后不得出现瞬移、穿模或速度异常
- 必须适配移动端触摸
- 必须适配桌面端鼠标
- 核心操作不得依赖 hover

**【键盘与可访问性】**

- 核心玩法必须提供与规则匹配的键盘操作
- 棋盘格、按钮和菜单必须有清晰焦点状态
- 需要时使用 aria-label、role、aria-live 等语义
- HUD 和结算文本必须能被屏幕阅读器读取
- Canvas 只负责视觉时，必须提供 DOM 操作入口或等价键盘入口
- 不能把关键玩法信息只画在 Canvas 内而没有文本或语义替代

**【规则执行与状态安全】**

- 任何被 engine 判定为合法的用户操作必须完整执行
- game、事件处理器、render 和 ui 层不得再次拦截、吞掉或伪装合法操作
- 渲染结果必须始终来自最新 engine state
- render 不得维护与 engine 冲突的规则状态
- Paused、GameOver 或其他不接受玩法输入的状态下，输入必须安全 no-op
- no-op 不得抛错
- 终止状态操作不得改变规则状态
- 若有随机逻辑，必须支持种子注入（PRNG）
- 解谜、固定关卡、发牌和路径生成必须保证可通关
- 挑战类玩法应保证数值增长平滑、可控，不制造系统性不可恢复死局
- 随机生成必须可以通过固定种子稳定复现

**【视口与页面布局】**

- 390px 宽移动端不得横向溢出
- 桌面端必须是宽屏游戏舞台
- 不得把整个桌面页面做成手机竖屏模拟
- 不得出现大面积黑边或生硬的竖屏容器
- 棋盘可以是正方形
- 桌面端按钮和 HUD 应集中在游戏区域附近
- 不得使用传统营销页、页头、页尾或大段说明占据主要游戏区域
- 必须适配 `@media (prefers-reduced-motion: reduce)`
- 关闭减少动效后，核心玩法和状态推进仍必须正常
- 只能减少装饰动画、粒子、震动和过渡，不得改变规则结果
